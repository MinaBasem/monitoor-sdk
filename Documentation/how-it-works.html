How It Works

Understanding the SDK's internals helps you debug integration issues, reason about performance, and evaluate its privacy guarantees.

The full pipeline

User action (button tap, screen view, etc.)
        ↓  synchronous write — always succeeds
SQLite buffer  (Library/monitoor_buffer.db)
        ↓  HTTP POST, batched
Ingest service  (server.py on your server)
        ↓  Neon HTTP SQL API
PostgreSQL Event table  (Neon)

Stage 1 — Local buffer

Every event is written to a SQLite database on the device before track() returns. This write happens synchronously on a dedicated serial queue and never blocks the main thread for more than a few microseconds.

The SQLite database is configured with:

  • WAL mode — writes are crash-safe. A power loss mid-write does not corrupt the database.
  • NORMAL sync — fast writes without full fsync on every row.
  • iCloud backup excluded — the buffer is not backed up to iCloud.

Events in the buffer have one of two statuses:

StatusMeaning
pendingWaiting to be sent. Will be retried indefinitely until retentionDays expires.
failedPermanently rejected by the server (HTTP 4xx). Will not be retried.

Stage 2 — Flush engine

The flush engine drains the buffer by sending events to the ingest service in batches. It is triggered by five conditions simultaneously:

TriggerWhen it fires
TimerEvery flushInterval seconds (default: 20s)
Batch fullWhen buffer reaches flushBatchSize events (default: 50)
App backgroundsUIApplication.didEnterBackgroundNotification — a background task keeps the process alive to finish
App terminatesUIApplication.willTerminateNotification — synchronous flush with 3-second deadline
Network restoredNWPathMonitor path becomes .satisfied

Drain loop

A flush does not send just one batch. It continuously sends batches of flushBatchSize events until the buffer is empty:

flush triggered
  dequeue 50 events
  POST /v1/ingest → 2xx
  delete 50 rows from buffer
  dequeue next 50 events
  POST /v1/ingest → 2xx
  delete 50 rows
  dequeue → 0 rows
  stop

This means if a device was offline for days and accumulated thousands of events, a single flush trigger will drain all of them as fast as the network allows.

Stage 3 — Retry behaviour

When a flush fails, the SDK responds based on the HTTP status code:

ResponseAction
2xxEvents deleted from buffer. Fetch next batch immediately.
4xx (client error)Events marked failed permanently. Not retried — the server has rejected them definitively.
429 Too Many RequestsBack off for the duration specified in the Retry-After header (defaults to 60s). Events remain pending.
5xx or network errorExponential back-off: 1s → 2s → 4s → 8s → … max 300s. Events remain pending.

Idempotency

Every event carries an idempotency_key formed from:

{device_id} + {session_id} + {occurred_at_ms}

The ingest service inserts with:

ON CONFLICT ("idempotencyKey") DO NOTHING

If the network drops after the server writes the events but before it returns 200, the SDK retries the same batch. The duplicate events silently no-op — the database always ends up with exactly one copy of each event.

Wire format

Each flush sends a single HTTP request:

POST {ingestURL}/v1/ingest
Authorization: Bearer mn_live_your_key
Content-Type: application/json
Content-Encoding: gzip  (when payload > 1 KB)
X-Monitoor-SDK-Version: 1.0.0

{
  "sdk_version": "1.0.0",
  "batch": [
    {
      "type": "event",
      "name": "play_pause_tapped",
      "session_id": "uuid",
      "device_id": "uuid",
      "user_id_hash": "sha256hex | null",
      "idempotency_key": "device_id-session_id-timestamp",
      "occurred_at": "2026-05-31T12:00:00.000Z",
      "properties": { "source": "mini_player" },
      "context": {
        "app_version": "1.0",
        "build": "1",
        "os": "iOS 18.0",
        "device": "iPhone 16 Pro",
        "locale": "en_US",
        "timezone": "Europe/London",
        "bundle_id": "com.example.app"
      }
    }
  ]
}

The server responds with a partial-acceptance response:

{
  "accepted": 49,
  "rejected": 1,
  "errors": [
    { "index": 12, "reason": "occurred_at is in the future" }
  ]
}

Valid events are stored even if some in the batch are rejected.

Clock skew protection

The ingest server rejects events where:

  • occurred_at is more than 5 minutes in the future (device clock ahead of server)
  • occurred_at is more than 7 days in the past (stale events beyond the retention window)

The server's received_at timestamp is always accurate regardless of device clock issues.
