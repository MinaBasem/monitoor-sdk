Event Tracking

Track any user action or application state change as a named event with optional properties. Events are the core data type in Monitoor — everything from button taps to purchases is ultimately an event.

Basic event

Call Monitoor.track() with a name to record that something happened.

Monitoor.track("song_played")
Monitoor.track("onboarding_completed")
Monitoor.track("settings_opened")

Event with properties

Attach a dictionary of properties to give the event context. Property values can be String, Int, Double, or Bool.

// String properties
Monitoor.track("song_played", properties: [
    "title": "Midnight Run",
    "artist": "Neon Atlas",
    "source": "library"
])

// Mixed property types
Monitoor.track("search_performed", properties: [
    "query":         searchText,
    "results_count": results.count,    // Int
    "used_filters":  filtersActive      // Bool
])

// E-commerce / subscription
Monitoor.track("plan_selected", properties: [
    "plan":         "pro_annual",
    "price":        49.99,            // Double
    "trial_active": true              // Bool
])

Timed events

Measure how long an operation takes by calling startTimer() at the start and track() with the same name at the end. The elapsed duration is automatically attached as $duration (seconds, as a Double).

// Start the timer when the operation begins
Monitoor.startTimer("onboarding_flow")

// ... user goes through onboarding ...

// Track completion — $duration is attached automatically
Monitoor.track("onboarding_flow")
// → event contains "$duration": 47.3

// Timer with additional properties
Monitoor.startTimer("file_import")

// ... import completes ...

Monitoor.track("file_import", properties: [
    "file_count": importedFiles.count,
    "format":     "mp3"
])
// → event contains "$duration": 1.24, "file_count": 5, "format": "mp3"
ℹ️
Multiple timers can run simultaneously. Each timer is keyed by event name and consumes itself when track() is called — calling track() a second time with the same name will not attach a duration unless you call startTimer() again.

Where to call track()

Call Monitoor.track() anywhere in your app code. It is thread-safe and safe to call from any queue.

// In a button action
Button("Delete") {
    model.delete(item)
    Monitoor.track("item_deleted", properties: ["id": item.id])
}

// In a view model
func submitForm() {
    guard isValid() else {
        Monitoor.track("form_validation_failed")
        return
    }
    submit()
    Monitoor.track("form_submitted")
}

// In an async context
func loadFeed() async {
    Monitoor.startTimer("feed_load")
    let items = await api.fetchFeed()
    Monitoor.track("feed_load", properties: ["count": items.count])
}

// In a SwiftUI .onChange or .onAppear
List(items) { item in ItemRow(item: item) }
    .onChange(of: filter) { _, newFilter in
        Monitoor.track("filter_changed", properties: ["filter": newFilter.rawValue])
    }

Event naming conventions

Consistent naming makes your dashboard far more useful. Follow these rules:

RuleGoodAvoid
Use snake_casesong_playedSongPlayed, song-played
Use noun_verb or noun_actionplaylist_createdcreated_playlist
Be specificmini_player_tappedbutton_tapped
Past tense for completed actionspurchase_completedpurchase_complete
Reserve $ prefix for system events—$my_event

System events

The SDK automatically sends these events — you do not call track() for them:

Event nameWhenProperties
$app_openApp launches or returns to foreground after a new session starts—
$app_backgroundApp moves to the background$session_duration_s
$screen_viewUIViewController appears, or .monitoorScreen() fires$screen_name
$revenueStoreKit 2 transaction or manual trackRevenue()product_id, amount, currency, type, transaction_id

Properties best practices

  • Keep property names in snake_case to match the event name convention.
  • Do not put PII (names, emails, phone numbers) in properties. Use Monitoor.identify() for user linkage instead.
  • Prefer discrete string values over free-text for properties you'll filter on ("source": "library", not "source": "user clicked from their music library").
  • Numeric properties (Int, Double) are stored as JSON numbers and can be aggregated in the dashboard.

Querying events

All events land in the Event table in Neon. Properties are stored as JSONB, enabling flexible queries:

-- Count plays per artist in the last 7 days
SELECT
    properties->>'artist' AS artist,
    COUNT(*) AS plays
FROM "Event"
WHERE
    name = 'song_played'
    AND "occurredAt" > NOW() - INTERVAL '7 days'
GROUP BY artist
ORDER BY plays DESC;
